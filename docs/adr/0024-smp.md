# ADR-0024 — SMP: setiap CPU menjalankan thread

- Status: diterima
- Tanggal: 2026-09-30
- Menggantikan: bagian "satu CPU" dari ADR-0006 (PIC dan PIT tetap seperti di sana)
- Konteks: PRD §7 K02 (penjadwalan dan isolasi), pertanyaan pengguna "mesin 16 core hanya dipakai
  1 saja", ADR-0006 (daftar penyederhanaan satu CPU yang harus diganti), ADR-0019 (uji stabilitas)

## Konteks

Sampai sekarang kernel hanya berjalan di CPU boot; CPU lain dibiarkan parkir oleh firmware. Profil
lab memberi 4 vCPU dan mesin sungguhan punya 4 sampai puluhan core, tetapi semua proses — model,
jaringan, desktop — antre di satu core. ADR-0006 mencatat tiga penyederhanaan yang bergantung pada
asumsi itu: stack `syscall` di satu global, spinlock yang hanya mematikan interrupt, dan penjadwal
tanpa kunci lintas CPU.

## Keputusan

**1. Menemukan dan menyalakan CPU.** MADT dari ACPI (RSDP sudah ada di `BootInfo`) memberi APIC ID
setiap CPU yang *enabled*; yang hanya *online capable* adalah soket hot-plug dan dilewati. Local
APIC dipakai dalam mode yang dipilih firmware — xAPIC lewat MMIO, atau x2APIC lewat MSR — dan
mengirim INIT, start-up, start-up. Trampoline berada di satu halaman di bawah 1 MiB (lima frame
disisihkan saat alokator frame dibuat, sebelum heap memakan semua frame rendah): real mode →
protected mode → long mode dengan NX dan WP, di atas tabel halaman kecil yang hanya memetakan
halaman itu sendiri dan separuh atas kernel, lalu lompat ke `ap_entry` di stack kernel bertanda
(guard page). Trampoline disimpan sebagai data di `.rodata`, karena ia disalin, tidak dijalankan di
tempat — dan gerbang build "tanpa FPU/vektor" tetap mendekode setiap instruksi 64-bit kernel. CPU
dinyalakan satu per satu; yang tidak menjawab dilaporkan, dikirimi INIT lagi (agar tidak pernah
menjalankan trampoline dengan nomor CPU lain), dan dibiarkan. Paling banyak 64 CPU; lebihnya
tetap parkir dan disebut di log.

**2. Apa yang dimiliki setiap CPU.** Satu GDT bersama dengan satu TSS per CPU, masing-masing dengan
stack IST sendiri. Nomor CPU dibaca dari selector TSS (`str`): tidak butuh `GS`, bekerja dari
konteks apa pun termasuk NMI. Stack kernel untuk `syscall` ditemukan lewat `swapgs` — hanya di stub
masuk, dua instruksi, lalu `swapgs` kembali; bagian kernel lain tidak pernah memakai `GS`. Setiap
CPU mematikan unit FPU/vektornya sendiri (CR0/CR4 per CPU) dan memprogram MSR `syscall`-nya.

**3. Penjadwal.** Satu run queue untuk semua CPU; setiap CPU punya thread idle, thread berjalan, dan
kuantum sendiri. Aturan `on_cpu`: sebuah thread hanya ada di run queue selama tidak ada CPU di
stack-nya. CPU yang meninggalkan thread memasukkannya kembali setelah switch selesai; wake-up yang
menemukan thread masih di CPU hanya menandainya `Ready`, dan CPU itulah yang mengantrekannya. Jadi
dua CPU tidak pernah berada di satu stack, dan tidak ada CPU yang menunggu CPU lain meninggalkan
stack — tidak ada deadlock saling tunggu.

**4. Waktu dan interrupt.** PIT (1 kHz) tetap di CPU boot dan tetap satu-satunya sumber waktu
(`ticks`, sleeper); PIC tetap mengirim IRQ perangkat hanya ke CPU boot, lewat LINT0 dalam mode
virtual wire yang disiapkan firmware. CPU lain memakai timer local APIC 100 Hz, dikalibrasi terhadap
PIT, hanya untuk mengakhiri kuantum 10 ms. CPU yang idle dibangunkan dengan IPI "ada pekerjaan"
setiap kali sesuatu masuk run queue.

**5. TLB tanpa shootdown.** Setiap proses punya satu thread, dan CPU selalu memuat CR3 thread yang
dituju pada setiap switch — CR3 kernel ketika idle. Maka tidak ada CPU yang masih memegang
terjemahan ruang alamat yang diubah CPU lain: proses hanya aktif di CPU yang menjalankannya. Stack
kernel dipetakan non-global; CPU yang memetakan slot yang dipakai ulang menjalankan `invlpg`
untuknya, dan CPU lain hanya menyentuhnya setelah menjalankan thread pemiliknya, yaitu setelah
memuat CR3.

**6. Kill ke thread yang sedang berjalan di CPU lain.** Kill yang datang ketika target belum tidur
tidak menemukan apa pun untuk dibangunkan. Setiap jalur tidur (`recv`, `wait`, `wait_any`, `sleep`)
kini memeriksa kill tertunda *setelah* menandai dirinya `Blocked` (`sched::block`), dengan fence
di kedua sisi: salah satu pihak selalu melihat pihak lain.

**7. Exit diumumkan setelah thread-nya dituai.** Dengan beberapa CPU, induk bisa berjalan pada saat
ia dibangunkan, ketika anaknya masih membebaskan memori di CPU lain. Status keluar kini diumumkan
oleh penuai thread, setelah stack kernelnya bebas: `wait` kembali berarti memori, handle, stack
kernel dan lease layar anak sudah kembali.

**8. Spinlock tahu pemegangnya.** Diminta lagi oleh CPU yang memegangnya → panic seketika
(sebelumnya: panic setelah sepuluh juta putaran). Ditunggu CPU lain adalah hal biasa; hanya
penantian berdetik-detik yang dilaporkan sebagai deadlock, dengan nomor kedua CPU.

**9. Panic.** CPU yang panic menghentikan CPU lain dengan NMI sebelum menulis laporannya; panic di
CPU lain pada saat yang sama hanya berhenti, agar laporan pertama selesai.

**10. Antrean penjadwal diberi ruang sekali, saat boot.** Run queue dan daftar sleeper disiapkan
untuk 256 thread sekaligus. Kapasitas keduanya hanya bisa tumbuh; tanpa ruang awal, heap kernel
naik untuk selamanya pada saat pertama kali paling banyak thread menunggu bersamaan. Di satu CPU
saat itu selalu jatuh di putaran pertama uji stabilitas; di beberapa CPU bisa jatuh kapan saja,
dan uji stabilitas (ADR-0019) benar membacanya sebagai heap yang tidak kembali ke tempatnya.

## Bukti

| Klaim | Bukti |
|---|---|
| Semua CPU yang tercantum dinyalakan dan menjalankan thread | log boot: `[kernel] smp: 4 CPUs online (boot CPU local APIC 0; started 1 2 3), xAPIC APIC mode, AP timer 100 Hz (…)`; seluruh suite penerimaan berjalan di 4 vCPU: `ALL TESTS PASSED (117/117, 0 skipped)` |
| Dua proses benar-benar berjalan bersamaan | K02 "two processes run at the same time on different CPUs": 200 giliran lewat satu word memori bersama, tanpa syscall di kedua sisi, dalam 1 ms di 4 CPU dan 3 ms di `i440fx` (2 CPU); di satu CPU setiap giliran menunggu preemption, minimal 2 detik |
| Kode yang sama di satu CPU | compat `q35-1cpu-2g`: `smp: one processor (local APIC 0)`; uji paralel dilewati dengan alasan "one CPU on this machine" |
| Kill ke thread yang sedang berjalan di CPU lain tidak hilang | K03 "20 kill-while-blocked cycles …": sebelum `sched::block`, run pertama di 4 CPU macet di siklus pertama — anak sudah menjawab tetapi belum kembali ke `recv` ketika kill datang |
| `wait` kembali setelah anak benar-benar hilang | U01 "the desktop takes the screen …" dan "a desktop that is killed gives the screen back …": sebelum keputusan 7, `lease after the desktop quit: resource busy` |
| Stabilitas di beberapa CPU | skenario `stress` (dua putaran suite plus putaran chaos di 4 vCPU): `STRESS PASSED`, 234 uji, 12 proses dibunuh acak, 0 kebocoran |
| Heap kernel tidak bergeser mengikuti puncak konkurensi | sebelum keputusan 10, run bukti pertama: `pass 2: LEAK against pass 1: kernel heap bytes +32`; salinan tanpa keputusan 10 yang mencatat pertumbuhan run queue menunjukkan `run queue room 8` tepat di putaran yang bocor (ADR-0019); sesudahnya `stress` lulus empat kali berturut-turut dan sekali lagi di run bukti, `0 leak(s)` |
| Matriks | `cargo xtask compat` 10/10: q35 dan i440fx, 1, 2 dan 4 CPU, `qemu64` dan `max` |

## Gigi

Setiap pelemahan dijalankan sendiri terhadap skenario `acceptance` di 4 vCPU, lalu dikembalikan:

| Pelemahan | Akibat |
|---|---|
| CPU lain tidak pernah mengambil pekerjaan dari run queue (semuanya berjalan di CPU boot) | `200 turns took 3987 ms: the two sides took turns on one CPU, not ran at once` — satu-satunya dari 117 uji yang gagal |
| Tidur tanpa melihat kill yang sudah datang (`sched::block` tanpa pemeriksaannya) | run macet sampai harness menghentikannya setelah 240 detik, di NET "killing the service fails its clients …": kill yang datang ketika `spacenet` masih berjalan di CPU lain tidak pernah mendarat. Run SMP pertama sebelum perbaikan macet dengan cara yang sama di K03 "20 kill-while-blocked cycles" |
| Exit diumumkan sebelum proses dibongkar (urutan zaman satu CPU) | `lease after the desktop quit: resource busy` dan `lease after the desktop was killed: resource busy` |
| Tanpa `on_cpu`: thread kembali ke run queue sebelum CPU-nya meninggalkan stack-nya, dan wake-up mengantrekan thread yang masih di CPU | panic setelah 5,5 detik: `unhandled kernel-mode page fault` di cpu 1 dengan `rip=0x00007fffefffffd0` — kernel "kembali" ke alamat stack user, karena dua CPU memakai satu stack kernel |

## Konsekuensi

- IOAPIC belum dipakai: IRQ perangkat hanya sampai ke CPU boot (virtio dipoll oleh tick PIT, keyboard
  dan serial lewat PIC). Throughput I/O tidak ikut naik dengan jumlah CPU; komputasi dan layanan
  ya.
- Satu run queue global tanpa afinitas: thread berpindah CPU sesukanya, dan kunci penjadwal adalah
  satu-satunya titik serialisasi. Cukup untuk puluhan CPU dengan beban lab; bukan untuk ratusan.
- Proses multi-thread belum ada. Menambahkannya berarti TLB shootdown (keputusan 5 bersandar pada
  satu thread per proses).
- Uji kebocoran di suite penerimaan kini menunggu mesin tenang sebelum membandingkan
  (`settled_stats`, `stats_back_to`, paling lama 500 ms): memori yang benar-benar bocor tetap hilang
  berapa pun lamanya menunggu, jadi gigi uji itu tidak berkurang.
- Mesin satu CPU (konfigurasi `q35-1cpu-2g`) menjalankan kode yang sama; uji paralelisme dilewati
  dengan alasan "one CPU on this machine".
